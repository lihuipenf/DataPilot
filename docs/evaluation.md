## 三个基线失败例子

1. 日期范围汇总回答“1500”，但其逐日小计同时写了350和1000，正确总额是1350。
2. 数据行数回答6条，真实数据是5条（表头不算数据行）。
3. 总额与最高商品的组合问题回答总额1500，正确是1350。

原始回答保留在 [逐题JSON](evaluation/live-results.json)，可自行复核，不只展示成功截图。
工具化增加了输入Token和延迟；不能只引用正确率而隐去这些代价。

## 评测方法和边界

- Agent：同一固定题集，核对实际执行工具的结构化字段，再检查答案中的数字、商品名称与中文。绘图额外验证PNG文件存在。
- 基线：同一模型、完整相同CSV、同组对话历史、同输出上限，但一次生成且没有工具；绘图题不参与比较。
- 两者评判并不完全对称：基线只做答案关键词校验，Agent还要求正确的工具结果。因此本报告不是严格学术消融实验。
- 关键词可能漏判同义表达或放过包含矛盾数字的回答，应配合人工审查；此次公开了原始结果。
- 这是**固定小数据上的单次功能回归**，不是未见数据测试、统计显著性结论或生产泛化准确率。没有据此声称行业领先。
- 离线演示26/26由规则路由得到，只证明演示流程可运行；它不是LLM评测。
- Token为服务返回量，单价未设置，故不编造费用金额；缓存、重试和实际账单可能不同。
- 此轮数据在鲁棒性审查前取得；后续修正导出、模式切换、CSV行宽和上下文边界，并追加回归。业务计算与题目未改。

## 复现

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
.\.venv\Scripts\python.exe -m evals.run_eval --mode demo
.\.venv\Scripts\python.exe -m evals.run_eval --mode live --baseline
```

实时评测需要本地DeepSeek密钥并产生API调用。模型服务可能更新，同一题集再次运行的结果和耗时也可能不同。
