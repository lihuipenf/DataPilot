# 维护分流与发布约定

维护者：[@lihuipenf](https://github.com/lihuipenf)。面向个人维护、本地单用户项目，不承诺固定答复、修复或合并时限。[帮助入口](../SUPPORT.md) · [贡献说明](../CONTRIBUTING.md) · [安全政策](../SECURITY.md)

## 用户入口

- 普通缺陷、功能建议、使用问题分别使用Issue选择页的Bug、Feature、Question表单。
- 安全漏洞使用SECURITY.md中的专用邮箱，不在公开Issue、PR或附件中讨论未经协调的利用细节。
- 提交前查阅已有Issue、启动教程和能力边界，使用合成数据及脱敏日志。
- 普通贡献者不显示空白Issue选项；GitHub仍允许拥有写权限的维护者创建空白Issue。表单和勾选项不是自动脱敏或防泄漏机制。

## 标签与分流

| 标签 | 用途 | 后续动作 |
|---|---|---|
| needs-triage | 新表单自动添加，等待维护者判断 | 检查重复、适用版本、范围和复现信息 |
| bug | 普通可复现缺陷 | 明确触发条件，必要时加入回归再修复 |
| enhancement | 功能建议 | 先判断是否符合销售CSV/本地分析范围，再讨论验收 |
| question | 安装、配置或用法问题 | 指向对应教程或解释口径与限制 |
| needs-reproduction | 缺少环境或最小复现 | 请求补充合成数据，不索取.env或完整数据库 |
| documentation | 文档错误或改进 | 修正当前文档，保留历史实验事实 |
| duplicate | 重复问题 | 链接原Issue并说明，不重复安排工作 |
| wontfix | 当前范围内不采纳 | 说明原因或已有替代方案，不等于否定使用者需求 |
| good first issue / help wanted | 明确且适合协作的任务 | 维护者判断后手动添加，不自动承诺辅导时限 |

needs-triage与needs-reproduction由维护者移除/更新；没有自动关闭久未回复Issue的机器人。若发现意外公开的有效凭据，应先撤销/轮换并私下协调，不以单纯删评论代替处置。

## PR与检查

PR目标为main，沿用仓库模板。CODEOWNERS将`@lihuipenf`作为代码归属；该文件不是强制合并保护，具体功能受GitHub仓库可见性和计划限制。

维护者检查问题与行为变化、合成复现、权限/数据影响、许可证及验证证据。分析逻辑修改应运行单元/集成与离线评测；文档修改检查链接与示例，不为形式新增测试。真实模型验证需显式选择，不把API费用转嫁给普通贡献者或CI。

CI使用只读仓库权限，并在checkout后不保留认证凭据；当前运行测试、离线评测、pip-audit、Bandit高危检查和Docker冒烟。检查结果用于人工审阅，不自动合并外部PR。已开启依赖漏洞告警；这不等于配置了自动修复PR或自动升级依赖。

## 发布与维护记录

1. 核对版本来源、变更记录、当前文档和受支持版本；保存历史评测原始计数，不改写旧实验。
2. 检查CI、敏感文件与源码包内容，保留LICENSE、SECURITY.md、SUPPORT.md及维护配置。
3. 按新版本建立标签/Release并上传源码ZIP与SHA-256，重新下载验证。
4. 已发布标签和附件不覆盖；纯说明补充可更新Release文字并链接固定文档提交。
5. 仓库可见性由所有者决定，维护配置和发布操作不会自动公开仓库；普通代码公开不代表可以公网部署无认证服务。

发布问题以Issue或PR记录；安全修复按私下协调结果披露，避免公开仍有效的密钥或真实业务数据。
